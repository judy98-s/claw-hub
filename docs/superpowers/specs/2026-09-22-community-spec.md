# 커뮤니티 탭 기획 — 사입 단가 비교 · 재고 교환 · 인형 순위

- **상태:** 기획 (구현 전). 결정이 필요한 항목은 §9에 모았다.
- **작성일:** 2026-09-22
- **선행:** [claw-hub 설계 스펙](./2026-09-21-clawhub-design.md)

---

## 1. 무엇을 만드나

claw-hub는 지금 **사고 처리 도구**다. 알림이 오면 30초 안에 끝내고 닫는 화면.
커뮤니티 탭은 성격이 다르다. **한가할 때 여는 화면**이고, 여기서 사장님이 답을
얻으려는 질문은 셋이다.

1. **"이거 내가 비싸게 산 건가?"** — 사입 단가 비교
2. **"이 안 나가는 재고, 누가 안 가져가나?"** — 재고 교환 장터
3. **"요즘 뭐가 잘 나가지?"** — 인형 순위·트렌드

기계 데이터는 못 본다. 하지만 **사장님이 얼마에 사서 얼마를 버는지**는 직접
등록할 수 있고, 그 데이터가 위 세 질문의 답을 전부 만들어낸다.

---

## 2. 가장 중요한 제약 세 가지

설계 전체가 여기에 맞춰져 있다. 먼저 읽어야 나머지가 말이 된다.

### 2.1 "도매 사이트를 긁어서 단가 비교" 는 그대로 하면 안 된다

이건 기술 문제가 아니라 **판례가 있는 법률 문제**다.

잡코리아 v. 사람인에서, 경쟁사 웹사이트를 크롤링해 **자기 사이트에 게재한**
행위가 저작권법상 데이터베이스제작자 권리 침해로 인정됐다. 서울고법
2016나2019365 — 손해배상 2억 5천만원 + 간접강제금 2억원, 총 4억 5천만원.
우리가 하려는 "여러 도매몰 가격을 모아서 한 화면에 보여준다"와 사실관계가
거의 같다.

여기에 실무적 장벽이 하나 더 있다. 토이토이·캐치돌·돌하우스 같은 B2B 도매몰은
**사업자 회원 로그인 후에야 도매가가 보인다.** 로그인해서 긁는다는 건
이용약관 위반이고, 계정 정지로 끝나면 다행인 종류의 일이다.

**→ 결정: 남의 가격표를 긁어오지 않는다. 사장님이 실제로 산 가격을 모은다.**

이게 회피가 아니라 오히려 더 좋은 데이터다. 도매몰 표시가는 수량 할인·배송비·
단골 단가를 반영하지 않는다. 사장님이 알고 싶은 건 표시가가 아니라 **최종
결제 단가**이고, 그건 어디에도 공개돼 있지 않다. 우리만 가질 수 있는 데이터다.

공식 경로가 열려 있는 곳만 예외로 쓴다:

| 출처 | 경로 | 비고 |
|---|---|---|
| 도매꾹 / 도매매 | 공식 Open API (API Key, JSON/XML) | 분당 180회, 일 15,000회 |
| 네이버 검색 트렌드 | 데이터랩 Open API | 무료, Client ID/Secret |
| 그 외 도매몰 | **쓰지 않음** | 표시가는 사장님이 직접 적는다 |
| Ali / Temu | 링크만 저장 | 가격은 사장님 입력값 |

### 2.2 커뮤니티는 매장이 한 곳이면 아무것도 아니다

"전국 사장님들의 평균 단가"는 사장님이 200명일 때 성립한다. 지금은 1명이다.
이걸 무시하고 만들면, 첫 사장님이 들어와서 빈 표를 보고 두 번 다시 안 연다.

**→ 결정: 1번 기능은 커뮤니티가 아니라 개인 장부로 먼저 만든다.**

사장님이 **자기 원가와 마진을 보려고** 사입을 입력한다. 혼자 써도 쓸모가
있다 — "이번 달 인형값 얼마 썼지", "이 인형 마진 얼마 남지". 그 입력의
**부산물**이 비교 데이터다. 매장 3곳이 모이면 비교가 켜지고, 30곳이 모이면
순위가 의미를 갖는다.

순서가 반대면 (비교부터 만들고 데이터를 모으려 하면) 아무도 입력하지 않는다.

### 2.3 전화번호를 화면에 박아두면 그건 수집당한다

사장님 요청은 "전화번호 적어놓고 직접 통화해서 중고 거래"다. 방향은 맞다 —
에스크로·결제 붙이면 만들 게 세 배가 되고, 인형 몇 상자 거래에 그건 과하다.

다만 번호를 평문으로 렌더링하면 **봇이 전부 긁어간다.** 하루면 된다.

**→ 결정: 로그인한 매장에만, 버튼을 눌렀을 때만 번호를 준다.**
서버는 누가 누구 번호를 열어봤는지 기록한다. 환불 건의 계좌 열람과 같은 원칙이다.

## 3. 기능 1 — 사입 장부 & 단가 비교

### 3.1 혼자 쓸 때 (1단계)

사장님이 인형을 들이면 한 건 등록한다. **30초를 넘기면 안 된다** — 넘기면
아무도 두 번째 건을 넣지 않는다.

```
인형 검색 → [쿠로미 중형 30cm]  ← 카탈로그에서 고름
어디서    → [캐치돌 ▾]
단가      → 2,300원
수량      → 60개
배송비    → 3,000원         ← 선택
영수증    → 📷 사진 1장      ← 선택
```

입력이 끝나면 바로 보이는 것:

- **개당 실단가 2,350원** (배송비 60개로 나눠 얹은 값)
- 내 재고에 60개 추가
- "지난번 같은 인형은 2,480원에 사셨어요" — 자기 이력과의 비교부터

### 3.2 여럿이 모였을 때 (2단계)

같은 인형에 매장 세 곳 이상의 기록이 쌓이면 비교가 열린다.

```
쿠로미 중형 30cm
─────────────────────────────
전국 평균   2,410원   (매장 12곳 · 최근 90일)
가장 싸게   2,150원   ← 도매꾹
내 단가     2,350원   ▍평균보다 60원 쌈
```

**보여주지 않는 것:**

- 어느 매장이 얼마에 샀는지 (매장명을 붙이면 아무도 안 올린다)
- 표본이 3곳 미만인 인형의 평균 (한 곳 가격이 곧 그 사람 가격이 된다)
- 90일보다 오래된 기록 (인형 단가는 환율과 물량에 따라 움직인다)

### 3.3 가장 어려운 문제: "같은 인형인가?"

한 사장님은 `쿠로미 중형`, 다른 사장님은 `산리오 쿠로미 30cm 인형`이라고
적는다. 이게 같은 것으로 묶이지 않으면 비교는 영원히 안 된다. 그리고 이건
자유 입력으로는 절대 안 풀린다.

**→ 카탈로그를 우리가 만든다.**

- 초기 300종 정도를 수기로 넣는다 (도매꾹 Open API + 주요 도매몰 상품명 참고).
  캐릭터 · 크기 · 브랜드가 축이다.
- 사장님은 **검색해서 고르기만** 한다. 입력이 아니라 선택이다.
- 없으면 "새 인형 등록 요청" → 운영자가 승인하며 중복은 병합한다.
- 미승인 항목은 내 장부에는 들어가지만 **비교 통계에는 안 들어간다.**

이 수작업을 피하려고 자유 입력을 허용하면, 6개월 뒤 "쿠로미"가 40개 항목으로
쪼개져 있고 그때는 손쓸 수 없다.

## 4. 기능 2 — 재고 교환 장터

### 4.1 등록

재고 장부가 이미 있으므로 등록은 **재고에서 한 번 탭**이다. 품명·수량·원가가
이미 시스템에 있다. 사장님이 새로 정하는 건 셋뿐이다.

```
쿠로미 중형 30cm · 42개 보유
─────────────────────────────
거래 방식  [ 판매 ] [ 교환 ] [ 둘 다 ]
내놓을 수량  40개
희망 단가   1,800원   (내 원가 2,350원)
한마디     "작년 물량이라 태그 있어요. 직거래만"
```

"교환"을 따로 둔 이유: 사장님이 원하는 건 현금이 아니라 **안 나가는 인형을
나가는 인형으로 바꾸는 것**인 경우가 많다. 판매만 있으면 그 수요가 표현이 안 된다.

### 4.2 목록

지역이 첫 필터다. 인형 상자는 택배로 보내면 배보다 배꼽이 크다.

```
[ 내 주변 ▾ 서울 ]  [ 판매 ] [ 교환 ]  [ 캐릭터 ▾ ]
─────────────────────────────────────────
(판매)  쿠로미 중형 30cm
        1,800원 · 40개
        강남구 · 2시간 전              [전화]

(교환)  짱구 대형 45cm
        20개
        송파구 · 어제                  [전화]
```

### 4.3 연락

`[전화]` 를 누르면:

1. 로그인 확인 (로그인 안 한 사람에게는 번호가 아예 안 나간다)
2. 서버가 열람 기록 — 누가, 어느 글의, 언제
3. 번호 표시 + `tel:` 링크

번호는 HTML에 **절대 미리 들어가지 않는다.** 버튼을 눌러야 API가 준다.
이게 봇 수집과 사람 사이의 실질적인 경계선이다.

### 4.4 사기·분쟁

돈이 오가지만 **우리는 결제에 개입하지 않는다.** 그래서 우리가 할 수 있는
일은 세 가지뿐이고, 그 이상을 약속하면 안 된다.

- **매장 인증이 게시 조건.** 사업자등록번호를 등록한 매장만 글을 쓴다.
  (국세청 사업자등록 진위확인 API로 자동 확인 가능한지 확인 필요 — §9 Q4)
- **신고 버튼.** 3회 신고되면 글이 자동으로 내려가고 운영자에게 알림.
- **문구를 분명히.** "claw-hub는 거래 당사자가 아닙니다. 직거래 시 실물을
  확인하세요." 하단에 항상.

30일이 지난 글은 자동으로 내린다. 죽은 글이 쌓인 장터는 안 여는 장터가 된다.

## 5. 기능 3 — 인형 순위 & 트렌드

### 5.1 "매일 긁어온다"를 어떻게 할 것인가

사장님 요청은 "매일 최신 트렌드를 긁어와서 순위를 보여달라"였다. 그대로 하면
§2.1의 문제에 걸린다. 대신 **합법적으로 매일 돌릴 수 있는 신호 세 개**를 쓴다.

| 신호 | 출처 | 무엇을 말해주나 | 한계 |
|---|---|---|---|
| **검색량** | 네이버 데이터랩 API (매일 1회) | 손님이 요즘 뭘 찾나 | 상대값(0~100), 절대 수치 아님 |
| **사입량** | 우리 장부 | 사장님들이 뭘 들이고 있나 | 매장 수에 비례해 정확해짐 |
| **사장님 투표** | 주 1회 한 줄 투표 | 실제로 뭐가 빠지나 | 주관적, 표본 적음 |

세 신호를 **하나의 점수로 합치지 않는다.** 합치면 "왜 1위인지" 아무도 모르고,
그 순간 그 순위는 아무도 안 믿는다. 나란히 보여주고 사장님이 읽게 한다.

### 5.2 공짜로 얻는 네 번째 신호: 재보충 주기

가장 강한 신호는 따로 있다. **같은 인형을 다시 들이는 간격**이다.

```
쿠로미 중형을 12개 매장이 평균 11일 만에 재보충 → 빨리 빠진다
짱구 대형을 8개 매장이 평균 52일 만에 재보충 → 안 빠진다
```

사장님이 추가로 입력할 게 전혀 없다. 사입 기록만 있으면 계산된다. 기계
데이터를 못 보는 상황에서 "실제로 뽑혀 나가는 속도"에 가장 가까운 대리 지표다.

재고를 매일 차감하게 만드는 설계는 하지 않는다 — 아무도 안 한다.

### 5.3 화면

```
이번 주 인형 순위                          9월 넷째 주
────────────────────────────────────────

1  쿠로미 중형 30cm
   검색 ▲ 34%   재보충 11일   사장님 82% "잘 나감"
   평균 사입가 2,410원

2  산리오 대형 45cm
   검색 ▲ 12%   재보충 18일   사장님 71% "잘 나감"
   평균 사입가 5,200원

3  ...
```

1~3위만 크게, 나머지는 줄 목록. **시상대 금은동 아이콘은 쓰지 않는다** (§7).

## 6. 정보 구조 — 같은 앱에 어떻게 넣나

접수함은 "알림 받고 30초 안에 닫는" 화면이고 커뮤니티는 "한가할 때 머무는"
화면이다. 성격이 반대라 섞으면 둘 다 나빠진다. 하단 탭으로 분리한다.

```
┌──────────────────────────────────────┐
│                                      │
│              (화면)                   │
│                                      │
├──────────────────────────────────────┤
│  접수함    재고     커뮤니티    더보기  │
│   (3)                                │
└──────────────────────────────────────┘
```

- **접수함** — 지금의 신고 처리. 미처리 건수 배지.
- **재고** — 내 사입 장부, 원가, 마진. **혼자 써도 쓸모 있는 곳.**
- **커뮤니티** — 상단 세그먼트 3개: `단가` · `장터` · `순위`
- **더보기** — 기계 관리, 연락처, 설정 (지금 탭에 있던 것들을 여기로)

기계 관리는 QR 뽑을 때만 열지 매일 열지 않는다. 하단 탭 자리를 차지할 이유가
없어서 `더보기`로 내린다. (탭 4개 — 하단 내비게이션은 5개를 넘기면 안 된다.)

> **Slack 링크로 들어온 화면에는 하단 탭이 없어야 한다.** 그 화면은 이 건
> 하나만 볼 권한으로 열린 화면이다. 탭을 그리면 눌리고, 눌리면 401이 뜬다.
> 지금 `admin/(shell)` 라우트 그룹 밖에 `claims/[id]`를 둔 이유와 같다.

## 7. 디자인 방향

목표는 **"사장님이 한눈에 알아보고 반하는"** 화면이다. 그 반대말이 무엇인지부터
분명히 해두는 게 빠르다.

### 7.1 하지 않을 것 (AI가 짠 티가 나는 것들)

| 금지 | 이유 |
|---|---|
| 보라→파랑 그라데이션 히어로 | 2023년 SaaS 랜딩의 기본값. 본 사람은 다 안다 |
| 카드 3개 나란히 + 상단에 동그란 아이콘 | 같은 이유 |
| 이모지를 아이콘으로 (🎯 📊 🚀) | 폰트마다 다르게 렌더링되고, 싸구려로 보인다 |
| "당신의 매장을 한 단계 위로" 류 카피 | 아무 정보가 없는 문장 |
| 모든 요소에 radius 16px + 그림자 | 위계가 사라진다. 다 떠 있으면 아무것도 안 떠 있다 |
| 숫자 카운트업 애니메이션 | 읽으려는 숫자가 움직인다 |
| glassmorphism / 반투명 블러 | 한글 가독성을 깎는다 |
| 빈 화면에 "데이터가 없습니다" 한 줄 | 할 일을 안 알려준다 |

### 7.2 할 것

**원칙 하나: 숫자가 주인공이다.**

이 화면을 여는 사장님은 감상하러 오지 않는다. `2,410원`, `11일`, `▲34%`를
보러 온다. 그래서 화면을 열면 **가장 먼저 눈에 들어오는 건 숫자 하나**여야 한다.

구체적으로:

- **카드가 아니라 표.** 도매를 하는 사람은 엑셀을 본다. 한 화면에 12줄이
  들어가는 밀도가, 3개 카드가 여백을 두고 떠 있는 것보다 좋다.
  (접수 화면의 밀도 규칙과 의도적으로 다르다. 저쪽은 한 손으로 길에서 쓰고,
  이쪽은 앉아서 본다.)
- **숫자는 `tabular-nums`.** 세로로 자릿수가 맞아야 비교가 눈으로 된다.
- **내 값은 굵게 + 왼쪽 세로 바.** 남의 평균과 내 값을 색으로만 구분하지 않는다.
- **색은 기존 토큰을 그대로 쓰되 커뮤니티 전용 악센트를 하나 더 둔다.**
  지금 `accent-600`은 "환불 보내기"의 색이다. 돈이 나가는 버튼의 색을
  "글 쓰기"에 재사용하면 근육 기억이 섞인다.
- **아이콘은 Phosphor 그대로.** 이미 쓰고 있고, 선 굵기가 Pretendard와 맞는다.
- **모션은 150~200ms, `transform`/`opacity`만.** 목록이 바뀔 때 위치가 튀지
  않게 하는 용도지 구경거리가 아니다. `prefers-reduced-motion` 존중.
- **빈 상태는 다음 행동 한 개.** "아직 기록이 없습니다" 가 아니라
  `[첫 사입 기록하기]` 버튼과, 샘플 한 줄을 흐리게 깔아 무엇이 생길지 보여준다.

**한 줄로:** *다나와의 밀도에 2026년의 여백을 준 화면.* 예쁜 대시보드가 아니라
**읽히는 표**다.

### 7.3 토큰 (제안)

기존 `globals.css` 토큰을 그대로 상속하고 **커뮤니티 액센트 한 색만 추가**한다.
색을 더 늘리면 "이 색이 무슨 뜻이지"가 생긴다.

```css
/* 커뮤니티 액센트: 짙은 자두.
   - accent-600(#0f7167, 청록)은 "환불 보내기"의 색이다. 돈이 나가는
     버튼의 색을 "글 쓰기"에 재사용하면 근육 기억이 섞인다.
   - ok(초록)/warn(앰버)/stop(빨강) 어느 것과도 색상환에서 떨어져 있다.
   - 보라 그라데이션의 그 보라가 아니다. 채도를 낮춘 납작한 단색이고,
     그라데이션으로는 절대 쓰지 않는다. */
--color-trade-50:  #fdf2f6;
--color-trade-600: #8a2f52;   /* 흰 배경 대비 약 7.5:1 */
--color-trade-700: #6d2441;
```

타입 스케일 — 새 폰트를 들이지 않는다. Pretendard 한 가족으로 충분하고,
두 번째 서체를 넣으면 서브셋 빌드가 두 배가 된다.

| 역할 | 크기 / 무게 | 쓰는 곳 |
|---|---|---|
| 지표 숫자 | 32px / 700 / `tabular-nums` | 평균 단가, 재보충 일수 |
| 표 숫자 | 16px / 600 / `tabular-nums` | 목록의 가격·수량 |
| 본문 | 16px / 400 / line-height 1.5 | 설명, 한마디 |
| 보조 | 13px / 400 / `--muted` | 지역, 시각, 표본 수 |

> **가운뎃점 주의.** `A · B · C` 형태의 메타 문자열은 영문 UI에서는 생성물의
> 흔한 티다. 한국어에서는 가운뎃점이 정상 문장부호라 사정이 다르지만,
> **한 줄에 두 개 이상 쌓이면** 그때부터는 똑같이 기계가 붙인 티가 난다.
> 장터 목록 한 줄에 `강남구 · 2시간 전 · 판매`처럼 세 토막을 잇지 말고,
> 거래 방식은 배지로 빼고 `강남구 · 2시간 전`까지만 남긴다.

### 7.4 접근성 (타협하지 않는 선)

- 본문 대비 4.5:1 이상. 회색 위 회색 금지.
- 터치 타깃 44×44 이상, 간격 8px 이상.
- 색만으로 뜻을 전하지 않는다 (▲/▼ 기호를 숫자 옆에 같이).
- 모든 입력에 보이는 `<label>`. placeholder는 라벨이 아니다.
- 순위·추세를 그래프로만 주지 않는다. 표가 항상 있다.

## 8. 데이터 모델 (초안)

```
dolls                 카탈로그. 우리가 관리한다.
  id, name, character, brand, size_cm, image_key, approved, merged_into

doll_aliases          "쿠로미 중형" = "산리오 쿠로미 30cm"
  doll_id, alias

purchases             사입 한 건. 이 테이블이 세 기능 전부의 뿌리다.
  id, store_id, doll_id, vendor, unit_price_krw, qty,
  shipping_krw, purchased_at, receipt_key, created_at

inventory             현재 재고 (purchases 에서 파생, 사장님이 보정 가능)
  store_id, doll_id, qty_on_hand, avg_cost_krw

listings              장터 글
  id, store_id, doll_id, kind(sell|swap|both), unit_price_krw, qty,
  note, region_code, status, expires_at, created_at

listing_contacts      번호를 누가 열어봤나 (감사 로그)
  listing_id, viewer_store_id, at

doll_votes            주간 투표. (store_id, doll_id, week) 유니크
  store_id, doll_id, week, verdict(hot|normal|cold)

trend_daily           외부 신호 스냅샷
  doll_id, day, source(naver|domeggook), value
```

기존 스키마와의 관계: `stores` 를 그대로 쓴다. 커뮤니티 테이블에는
`store_id` 가 들어가지만 **매장명은 비교·순위 화면에 절대 나가지 않는다.**
장터 글에서만 나간다 — 거기서는 누구와 거래하는지 알아야 하니까.

`purchases.unit_price_krw` 는 암호화하지 않는다. 개인정보가 아니고, 통계를
내려면 SQL에서 집계해야 한다. 다만 **매장 단위로 식별 가능한 형태로는 절대
API 밖으로 내보내지 않는다.**

## 9. 결정이 필요한 것들

진행 전에 답이 필요한 것만 추렸다. 각 항목에 내 추천을 붙였다.

❓ **Q1 — 출시 순서**: 셋을 동시에 내면 전부 빈 화면으로 시작한다. 어떤 순서로?

➡️ **재고 장부 → 장터 → 단가 비교 → 순위.** 재고 장부는 혼자 써도 쓸모가
있어서 데이터가 쌓인다. 장터는 매장 5곳이면 이미 돌아간다. 단가 비교는 같은
인형에 3곳, 순위는 30곳쯤 필요하다. 앞의 것이 뒤의 것의 연료다.

---

❓ **Q2 — 카탈로그 초기 구축**: 인형 300종을 누가 넣나? 수작업이 꽤 든다
(항목당 이름·캐릭터·크기·사진 = 대략 2~3분, 총 12~15시간).

➡️ **도매꾹 Open API로 초안을 뽑고 사람이 다듬는다.** API로 "인형뽑기 인형"
카테고리 상품명을 긁어 캐릭터·크기를 추출하면 절반은 자동으로 채워진다.
나머지를 손으로 정리한다. 이 단계를 건너뛰면 §3.3의 문제가 영구적으로 남는다.

---

❓ **Q3 — 영수증 사진**: 사입 기록에 영수증을 **필수**로 할까 선택으로 할까?
필수면 데이터 신뢰도가 오르고, 선택이면 입력이 10배 쉬워진다.

➡️ **선택.** 다만 영수증이 붙은 기록에는 배지를 달고, **평균 단가 계산에는
영수증 있는 기록에 가중치를 더 준다.** 필수로 하면 아무도 두 번째 건을 안 넣는다.

---

❓ **Q4 — 매장 인증**: 장터 글쓰기에 사업자등록번호를 요구할까?

➡️ **요구한다.** 국세청 사업자등록 진위확인 공개 API가 있는 것으로 보이는데,
실제 사용 가능 여부와 조건은 확인이 필요하다. 자동 확인이 안 되면 1단계는
번호 형식 검증 + 운영자 수동 승인으로 간다. 인증 없이 열면 첫 달에 사기 글이 온다.

---

❓ **Q5 — 지역**: 장터 필터의 지역을 어디서 가져오나? 매장 주소를 아직 안 받고 있다.

➡️ **시·군·구 단위만 매장 설정에 추가한다.** 상세 주소는 받지 않는다 — 장터에
필요한 건 "가까운가"뿐이고, 상세 주소는 받는 순간 지켜야 할 것이 하나 더 는다.

---

❓ **Q6 — 순위의 공개 범위**: 인형 순위를 **비로그인 공개 페이지**로도 열까?

➡️ **연다 (읽기만).** 이게 유일한 유입 경로다. "2026년 9월 인형뽑기 인기 인형
순위" 페이지는 검색으로 사장님이 찾아온다. 단, 단가는 **로그인해야 보인다** —
그게 가입할 이유다.

---

❓ **Q7 — 하단 탭 구성**: §6의 `접수함 / 재고 / 커뮤니티 / 더보기` 로 가고
기계 관리를 `더보기`로 내리는 게 맞나?

➡️ **맞다고 본다.** 기계 관리는 QR 뽑을 때만 연다. 다만 지금 매일 쓰시는
화면이 무엇인지는 내가 아니라 사장님이 안다 — 여기만 확인 부탁드린다.

## 10. 하지 않을 것 (명시)

범위를 지키려고 적어둔다. 나중에 "이것도 넣자"가 나오면 여기를 먼저 본다.

- **결제·에스크로.** 장터는 직거래다. 돈에 개입하면 분쟁 처리 조직이 필요해진다.
- **채팅.** 전화가 더 빠르고, 채팅을 만들면 운영·신고·차단이 딸려온다.
- **도매몰 자동 주문/연동.** 계약 없이는 불가능하고, 계약해도 몰마다 다르다.
- **매장별 단가 공개.** 익명 집계만. 이걸 깨면 아무도 안 올린다.
- **기계별 뽑기 확률·매출 추정.** 기계 데이터가 없다. 추정치를 숫자로 보여주면
  그건 거짓말이다.
- **AI 추천 ("이 인형을 들이세요").** 데이터가 충분해지기 전까지는 근거 없는
  말이 된다. 순위를 보여주고 판단은 사장님이 한다.
